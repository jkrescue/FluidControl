# Public-data PhysicsNeMo case: actuated fluidic pinball

Status on 2026-09-27: **real-data field forecasting passes simple baselines; open-loop optimum prediction remains exploratory**. This is not a reproduction of the PolyU Yeung–Tang water-tunnel geometry, nor a closed-loop controller. HydroGym is not used at this stage.

## Source and physical setup

- Rodríguez-Asensio et al., *On the turbulent wake of the actuated fluidic pinball: dynamics, bifurcations and control authority*, [paper](https://arxiv.org/abs/2602.17713), [data DOI 10.5281/zenodo.20794709](https://doi.org/10.5281/zenodo.20794709).
- Three equal `D=30 mm` cylinders form an upstream-pointing equilateral triangle; center spacing `1.5D`. Front cylinder is stationary; rear cylinders counter-rotate at constant, symmetric settings. Water tunnel `U∞=0.31 m/s`, `Re=9100`. The action is `p=(b₃−b₂)/2` with `bᵢ=ΩᵢD/(2U∞)`, measured at 28 nominal values from `−2.8` to `2.6`.
- Original measurements: time-resolved PIV at 120 Hz (approximately 1800 snapshots per actuation) and drag coefficient `CD`. The paper also reports a companion 2-D Fluent URANS study; its released force table is numeric, while released `.hsf` vorticity files are visualization streams, not ready-made numeric grids.
- PolyU [Yeung's thesis](https://theses.lib.polyu.edu.hk/handle/200/14670) instead uses one larger main cylinder and two smaller downstream rotating cylinders. The PolyU repository page provides a thesis PDF, but no separate machine-readable flow fields were found. These cases must not be conflated.

## Integrity and conversion

`scripts/verify_source.py` checked all three archived Zenodo files against the record's exact byte sizes and MD5 values, then tested both ZIP archives; result: `artifacts/source_verification.json` (all verified). Raw files remain in `data/raw/zenodo_20794709/`.

`scripts/prepare_piv.py` reads the actual HDF5 layout (`[snapshot, x-index, y-index]`, despite the README describing another ordering), transposes space to `[y,x]`, converts raw pixel displacements to `u/U∞,v/U∞` using `0.29076921 mm/px × 120 Hz / 0.31 m/s`, and converts coordinates to `x/D,y/D`. It retains every sixth frame (20 Hz), resizes the physical `34×52` oriented grid to `32×64`, and saves data/validity masks per case under `data/processed/piv/`. The manifest records source file, control, drag, dimensions and transform; no vectors were missing in the released cases processed here.

`scripts/validate_processed_piv.py` passes structural, finite-value, case-count and split-leakage checks (`artifacts/processed_piv_validation.json`). The real PIV comparison generated by `scripts/plot_public_piv.py` is `artifacts/piv_baseline_vs_boattailing.png`; it shows the narrower, faster-recovering wake at measured `p=1.8` relative to `p=0`.

There are 57 HDF5 files: 28 unactuated `_zero` references are **excluded** because their `p` metadata refers to the subsequent controlled case, not their actual no-rotation state. Of the 29 retained controlled files, one is an extra upward wake branch at `p=−1.4`. The current single-branch model uses one documented file per nominal `p`, yielding 28 distinct control values.

The released experimental `Uncertainty` vector contains only NaNs. `CD` values are real, but no usable per-case numeric uncertainty is available from that file; the manifest represents missing uncertainty as `null`. Do not fabricate confidence intervals from it.

## Model A: fixed-actuation PIV dynamics (working field surrogate)

`scripts/train_piv_dynamics.py` trains a PhysicsNeMo 2-D FNO to map a measured `(u,v)` field, spatial coordinates, validity mask and fixed control `p` to a field 0.1 s later (roughly `1.03D/U∞`). Train/validation/test are split by **entire actuation value**, not by neighboring snapshots:

| Split | Held control values |
| --- | --- |
| Validation | `−1.0`, `1.0` |
| Test | `−1.8`, `1.8` |
| Training | Other 24 values, including `0` |

After validation-based checkpoint selection (`best_epoch=38` of 40), masked velocity MAE normalized by `U∞` is:

| Evaluation | PhysicsNeMo FNO | Copy-current-field baseline | Interpolated training-case temporal-mean baseline |
| --- | ---: | ---: | ---: |
| Validation | 0.0782 | 0.1316 | 0.1282 |
| Test | 0.0669 | 0.1243 | 0.1218 |

The FNO improves the unseen-control test MAE by about 46% versus persistence and 45% versus the conditional-mean baseline. These are offline, one-step forecasts of real PIV fields. They do **not** prove long-horizon CFD fidelity, force prediction, or safe actuation switching.

Artifacts: `artifacts/public_piv_dynamics_fno.pt`, `.json`. Reproduction:

```bash
CUDA_VISIBLE_DEVICES=0 .venv/bin/python scripts/verify_source.py
CUDA_VISIBLE_DEVICES=0 .venv/bin/python scripts/prepare_piv.py
CUDA_VISIBLE_DEVICES=0 .venv/bin/python scripts/train_piv_dynamics.py
```

## Model A2: PIV-to-drag observer (working measurement model)

`scripts/train_piv_force_observer.py` trains a second, small PhysicsNeMo FNO to estimate measured `CD` from a PIV velocity field and its coordinates. It deliberately receives **no `p` input**, so it cannot merely memorize an action-to-drag lookup. The same actuation-wise validation/test split is used. On full-case mean fields at the unseen controls, it predicts:

| Held-out `p` | Measured `CD` | PIV observer | Linear interpolation using training `p,CD` |
| --- | ---: | ---: | ---: |
| `−1.8` | 4.022 | 3.550 | 3.429 |
| `1.8` | 0.926 | 1.210 | 1.298 |

The two-case test MAE is approximately 0.378 for this observer versus 0.482 for the action-only interpolation. This is a useful force-estimation component for future feedback, **not** an action-to-drag model: the controlled flow must already have been observed. It cannot by itself choose an untested action. Artifacts: `artifacts/public_piv_force_observer.pt`, `.json`.

## Model B: mean-field/drag open-loop surrogate (not yet reliable at the optimum)

`scripts/train_public_piv.py` trains a second PhysicsNeMo FNO from baseline mean flow, coordinates and constant `p` to controlled mean `(u,v)` and measured `CD`. The split is identical; the best epoch is selected using only validation controls. On the two held-out controls the model's mean-field MAE is `0.0294` and `0.0548` in `U∞` units, better than simply reusing the uncontrolled field (`0.1587`, `0.2826`), **but worse than linear interpolation between neighboring measured training controls** (`0.0171`, `0.0345`). Its held-out `CD` errors are about `−0.596` at `p=−1.8` and `+0.559` at `p=1.8`; linear drag interpolation is also imperfect, especially at the sharp experimental minimum.

Searching the FNO-predicted drag curve suggests `p≈1.45`, whereas the lowest discrete experimental drag is at `p=1.8` (`CD≈0.926`). The recommendation is therefore a low-drag *region*, not a verified discovery of the optimum. Rounding to an actually measured control setting gives `p=1.4`, which is **already in the training set**; its measured `CD≈1.051` is lower than uncontrolled `CD≈3.017`, but that does not establish generalization. The production controller should not be accepted on this result alone.

Artifacts: `artifacts/public_piv_fno.pt`, `.json`. Reproduction:

```bash
CUDA_VISIBLE_DEVICES=0 .venv/bin/python scripts/train_public_piv.py --epochs 200
CUDA_VISIBLE_DEVICES=0 .venv/bin/python scripts/train_piv_force_observer.py
```

## Cross-source force check and limitations

`scripts/compare_force_sources.py` compares the paper's measured force table with its numerical URANS force table using linear interpolation to the coarser URANS `p` grid. The published URANS discrete minimum is `p=1.5`, `CD≈1.039`; the experimental discrete minimum is `p≈1.8`, `CD≈0.926`. Agreement is close near `p=1.5–2.0` but noticeably poorer at the high-actuation end (`p=2.5`), so URANS must not be treated as ground truth. Exact values are in `artifacts/published_force_comparison.json`.

Important next gates before calling stage 1 a validated *control* reproduction: assess several held-out controls (not only two), quantify training/seed variability, evaluate long-horizon prediction and physically meaningful drag/wake trade-offs, and independently validate any self-generated CFD data using the criteria in [CFD_DATA_GENERATION.md](CFD_DATA_GENERATION.md). Then, and only then, consider an interactive HydroGym extension.
